# LifeOS UX/UI audit, 2026-09-08

## Outcome and scope

The app now uses the owner's homelab Mira component library, direct grouped
navigation, shorter decision text, and two explicit Homelab decision actions.
The audit covered the shared shell, Today, decision and approval flows,
Assistant, common controls, and the main route layouts. It is a focused
implementation audit, not a full WCAG conformance certification.

## Accessibility findings

| Finding | Impact | Change | Verification |
| --- | --- | --- | --- |
| High: off-canvas navigation was still present without modal focus management (2.1.1, 2.4.3) | Keyboard focus could reach controls outside the visible mobile task | Base UI navigation sheet with focus trap, Escape and focus return | Tab through the complete mobile menu, then Escape |
| High: underlying decision cards remained accessible (1.3.2, 2.4.3) | Readers and keyboard users encountered multiple cards at once | Inactive cards and exit copies are inert and aria-hidden | Only the top card participates in interaction |
| High: fixed decision-card height (1.4.10) | Long descriptions could overlap the controls | Active card stays in normal flow; decision actions remain reachable | Expand a long fixture at 390px and 320px |
| Medium: nested main landmarks from the source sidebar | Ambiguous page landmark | Adapt SidebarInset to a div | One main landmark in the rendered app |
| Medium: invisible tooltips consumed Escape on the mobile sheet | Closing took a second keypress | Tooltips mount only for the collapsed desktop rail | Escape closes the mobile sheet on the first press |
| Medium: Assistant lacked consistent modal behavior on phones | Focus could leave the visible panel | Base UI Dialog, modal on mobile and nonmodal on desktop | Tab containment, outside interaction on desktop, Escape and return focus |
| Medium: route and filter state were visual only | Selected location was harder to identify | aria-current on navigation; aria-pressed on filters | Approvals alone owns its active state |
| Medium: source icon links lacked names (2.4.4) | Screen readers announced an unlabeled link | Explicit source and card link labels | Inspect rendered accessible labels |

Existing focus rings, pinch zoom, and reduced-motion support remain. Mobile
inputs remain 16px; primary touch controls are at least 44px high. Increased
contrast and reduced transparency settings receive explicit token treatment.
Screen-reader speech output and the entire set of feature forms were not
manually audited, so no overall WCAG pass level is claimed.

## Visual design

DM Sans, neutral zinc surfaces, a consistent radius, and the Mira control
family replace the old Aurora treatment. Existing feature imports consume the
new buttons, cards, inputs, textareas, badges, and skeletons. Sidebar and
mobile sheet use the source library's compositions. Existing Radix overlays
keep compatible parts, sharing the new tokens. The chart kit remains in use.

The source library's tiny catalog controls and layout/color transitions were
adapted for LifeOS touch targets and compositor-only motion. No new
transition-all or width/height transitions are imported from the catalog.

## Navigation and usability

| Before | After |
| --- | --- |
| Eight desktop destinations hidden behind More | Direct links in named groups |
| Approvals required entering Decide first | Its own sidebar link |
| Sidebar, mobile nav, and header carried separate route lists | One inventory with segment-aware matching |
| Today repeated complete triage lists | Compact counts and a direct decision link, with the full daily snapshot available |
| Decision text repeated the item title inside its outcome | Short outcome sentence; original summary can be expanded |
| Approval brief mixed consequences with raw instructions | Consequences stay visible; exact instructions are secondary |
| Repeated long explanation in the Assistant | Default of 60 words, preserving risks and conditions |

No functioning route was deleted based on an unimplemented retirement spec.
No saved content, task state, vault content, or live database was modified by
the redesign work.

## Homelab options

- Queue skill install: a fixed, scoped installation request referencing the
  stored source ID is queued for Claude. The existing Send action starts it.
  The app never claims queuing means installation succeeded.
- Save UI reference: the URL is logged once in the document store and can
  resurface for matching UI work in the Assistant and dispatch panel. Agents
  receive the lookup endpoint when queued work is dispatched.

Both paths use explicit typed actions. Source text cannot become a dispatched
instruction. Skill requests preserve manual queued work. Undo only cancels
an unsent request, and reference Undo preserves saves made through other
items. Effects and triage state updates are transactional.

## Verification

- TypeScript: `npx tsc --noEmit`, passed.
- Tests: 86 files, 962 tests passed. Existing tests were preserved.
- Lint: `npx eslint src --quiet`, no errors.
- Production: `docker compose build`, passed.
- Browser: synthetic approval, correction, Undo, failure recovery, source
  expansion, keyboard guards, desktop collapse, mobile focus trap and return,
  reduced motion, and 320px reflow. Both Homelab choices reach their typed
  action route, and matching references appear in Send to Claude. Homelab persistence, instruction-boundary,
  deduplication, matching, and Undo behavior use throwaway database tests.
- Main route smoke: Today, Content, Projects, Knowledge, Leads, Finance,
  Training, Voice, Status, Settings, Recipes, News, and Send to Claude rendered
  with no uncaught browser exceptions and no horizontal page overflow at the
  tested desktop width. The Projects read can remain in its existing
  asynchronous scan state, so this does not assert a completed live scan.

The review server uses a temporary filesystem, no live volumes, and disabled
schedulers. Browser mutation tests use synthetic responses; other route
reviews proxy read requests only. Screenshots stay in the ignored local
`.scratch/mira-redesign` directory because some contain personal content.

Actual skill installation, external integrations, and generated Assistant
reply length require their runtime services; the review did not execute an
installation or call the model. The reply-length rule is a prompt instruction,
not a hard truncation of model output. Production deployment is separate from
these local and isolated checks.
