# P02: User experience and content design

Checked: 2026-09-29. Scope: complete user journeys, information architecture, understandable language, accessibility, localization, and recovery. Recommended baseline: design and evaluate against WCAG 2.2 AA for web content, with platform accessibility behavior for native apps. Applicable law and a conformance claim require their own scoped assessment.

## Evidence and principles

Usability evaluation observes representative people performing realistic tasks. Nielsen Norman Group distinguishes this from gathering opinions and warns that task wording can influence behavior. Use a neutral scenario, not instructions that reveal the control the participant should find. Interviews, expert reviews, automated tests, and observed tasks answer different questions. [Usability testing](https://www.nngroup.com/articles/usability-testing-101/).

Write interface language with the same care as interaction structure. GOV.UK recommends direct wording, meaningful link text, labels associated with controls, and fixes to confusing interfaces rather than more explanatory copy. This is public-service guidance, not a rule that every consumer app must sound like government. Translate the principle into the product's chosen voice. [Writing for interfaces](https://www.gov.uk/service-manual/design/writing-for-user-interfaces).

WCAG is the normative web accessibility reference. W3C's Understanding documents explain individual criteria but are informative guidance. The July 2026 WCAG-EM 2.0 Group Note adds an evaluation procedure covering digital products, including native and cross-platform applications, without adding WCAG requirements. Its sampling method alone does not support a whole-site conformance claim. [WCAG 2.2](https://www.w3.org/TR/wcag/), [WCAG-EM 2.0](https://www.w3.org/TR/wcag-em-2/).

Prefer native elements and established primitives for complex controls. ARIA supplies semantics, not keyboard behavior; the Authoring Practices Guide also requires testing relevant browser and assistive-technology combinations. A component library's accessibility statement is input to review, not proof that your composition is usable. [ARIA practices and support caveats](https://www.w3.org/WAI/ARIA/apg/practices/read-me-first/).

## The Micro workflow

1. **Map the complete task.** From the discovery brief, record the entry point, desired outcome, information needed, decisions, external dependencies, success, and recovery. Include acquiring the app, first value, returning later, permissions, support, and leaving. For budgeting, “add an expense” includes selecting the date and currency, validating the amount, saving, confirming the resulting budget, and correcting a mistake.
2. **Choose the navigation model.** Identify the user's terms and the few places they must distinguish. Test a simple flow or navigation prototype before building a complex hierarchy. Preserve browser Back and deep-link expectations on web; define platform Back behavior and interrupted sessions on mobile.
3. **Make a state inventory.** Cover the states that actually exist: empty, partial, loading, pending, success, invalid input, failed network, denied permission, expired session, conflict, and retry. Specify what persists after refresh or app restart. Do not produce a happy-path screen and leave engineers or agents to invent the rest.
4. **Write real content.** Include representative names, labels, instructions, errors, prices, dates, privacy decisions, and help. Every error identifies the problem and a possible next step without disclosing sensitive internals. Destructive actions state their consequence. Place help beside the control it explains.
5. **Prototype uncertain interactions.** Use a low-cost artifact appropriate to the question, then observe likely users. Keep the task neutral: “You entered yesterday's expense twice; correct your budget” is more informative than “Press Delete on the second card.” Note assistance, misunderstanding, failure, and successful recovery.
6. **Implement and assess real behavior.** Combine automation with keyboard, screen-reader, touch, zoom, and device checks. Reassess after meaningful changes because design-stage evidence can become obsolete in the implementation.

Recommended artifacts:

| Artifact | Contents |
| --- | --- |
| `journeys.md` | Task steps, entry/exit, interruptions, dependencies, recovery |
| `ui-state-matrix.md` | State, trigger, visible content, allowed actions, persistence, focus/announcement behavior |
| `content.md` | Product terminology, labels, validation/recovery text, language and format rules |
| `usability.md` | Research question, participant criteria, neutral tasks, observations, limitations, changes |
| `accessibility.md` | Target, evaluated product/build, views and complete processes, device/assistive-technology baseline, findings |

These documents can be sections in one feature spec. Separate them when reuse or complexity justifies it. Use synthetic financial examples and retain participant information outside public source control.

## Checks that change the design

WCAG 2.2 AA includes accessible authentication and focus not being entirely hidden by author-created content. Test password-manager support, paste, login error recovery, and the relevant alternatives to cognitive tests. Check focus beneath sticky headers, cookie banners, and bottom actions. Do not confuse the AA focus criterion with the stricter AAA requirement for full visibility. [Accessible authentication](https://www.w3.org/WAI/WCAG22/Understanding/accessible-authentication-minimum.html), [New WCAG 2.2 criteria](https://www.w3.org/WAI/standards-guidelines/wcag/new-in-22/).

For relevant legal commitments, financial transactions, and user-controlled data changes, WCAG 3.3.4 requires a reversible, checked, or confirmed submission. Apply a proportionate recovery design: undoing an ordinary expense edit may be more useful than a confirmation dialog for every click. A destructive account removal or external transfer needs a different contract. [Error prevention](https://www.w3.org/WAI/WCAG22/Understanding/error-prevention-legal-financial-data.html).

Reflow checks should consider the criterion's exceptions for content needing a two-dimensional layout. A data table can legitimately require horizontal movement; that does not excuse an entire form overflowing. Check readable content and usable controls at the relevant zoom and width. [Reflow](https://www.w3.org/WAI/WCAG22/Understanding/reflow.html).

Localization includes text direction, language metadata, Unicode input, names, addresses, dates, and numeric formats. Avoid composing translated sentences from disconnected string fragments. For budgeting, record currency and date semantics separately from display formatting; test French decimal input and long translated labels. Add right-to-left cases when supported markets require them. [W3C internationalization guidance](https://www.w3.org/International/quicktips/).

## Risk-tiered acceptance

| Tier | Observable predicate |
| --- | --- |
| Prototype | The main task and a meaningful failure state can be attempted; observations distinguish user evidence from reviewer guesses; no participant enters undisclosed real sensitive data |
| Public release | Every critical journey passes browser/device acceptance; all actionable controls have usable semantics and focus; relevant keyboard, zoom, touch, and screen-reader tasks pass the recorded matrix; known barriers and evaluation scope are disclosed |
| Sensitive or consequential flow | Recovery, confirmation/undo where applicable, session expiry, authorization failure, and inaccessible external dependencies have explicit evidence; specialist accessibility/domain review covers critical processes |

Automated accessibility tools detect only part of the problem space. W3C explains that human judgment remains necessary. An axe or Lighthouse pass is one result, never an accessibility certification. Report the checked views, build, tools, manual cases, and unresolved findings. [Selecting evaluation tools](https://www.w3.org/WAI/test-evaluate/tools/selecting/).

## Tools, implementation, and limits

Use Playwright for web journey assertions, an accessibility scanner for known machine-detectable violations, and a fixture route or Storybook for repeatable states. Use VoiceOver or TalkBack on actual mobile flows and the relevant desktop screen reader/browser combinations. Native UI needs device evidence; a desktop browser screenshot of an Expo app is insufficient. Android guidance recommends at least 48dp touch targets, a platform recommendation distinct from CSS-pixel WCAG thresholds. [Android accessibility](https://developer.android.com/guide/topics/ui/accessibility/views/apps-views).

Start by requiring a task-and-state contract for each first-release feature. Next add accessibility scope and manual checks to review evidence. Then expand localization and usability research around actual target markets and uncertain journeys. Choose one UX review skill that understands these artifacts; reserve AppLlama for observed reference patterns. Require the skill to report unknowns instead of inventing research.

The retained Micro brief/templates support feature acceptance text and design references. The earlier LifeOS studio exposed those fields at [historical revision e04f14e](https://github.com/Samylay/LifeOS/tree/e04f14e/app/src/app/micro); concurrent user work removed its UI and API from the current checkout.
