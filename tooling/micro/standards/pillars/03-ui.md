# P03: Visual UI and design systems

Checked: 2026-09-29. Scope: visual direction, typography, layout, semantic tokens, reusable components, platform conventions, and design-to-code handoff. This guide recommends a shared quality floor and a distinct visual identity per product. It does not prescribe one aesthetic or require a separate design-system team.

## Evidence and principles

Emil Kowalski's public “Agents with Taste” article explains how explicit craft rules help agents make more consistent decisions. Treat those rules as an experienced author's design doctrine. They do not replace accessibility standards, user research, or measurement. His public skills provide concrete task-specific engineering guidance, including library selection, mobile web behavior, and animation review. [Agents with Taste](https://emilkowal.ski/ui/agents-with-taste), [Upstream skills at the reviewed revision](https://github.com/emilkowalski/skills/tree/d16ebe60d09a5ba2afcb7054ede9d0a10c9f6128).

A reusable pattern earns its place through actual use. GOV.UK's contribution criteria require evidence that a proposed component is useful and unique, then usable, consistent, and versatile. Adapt this into a small factory rule: reuse an existing good control first, and promote a new abstraction only after its purpose and variations are understood. Do not copy GOV.UK branding into an unrelated consumer app. [Contribution criteria](https://design-system.service.gov.uk/community/contribution-criteria/).

The DTCG 2025.10 format is a stable Community Group report for token interchange. It is explicitly not a W3C Standard. The September 2026 draft warns implementers not to adopt that draft as authoritative. A single app can start with CSS variables; introduce an interchange format when design tools, multiple platforms, or generated outputs need it. [Published token format](https://www.designtokens.org/TR/2025.10/format/), [Draft status](https://www.designtokens.org/tr/drafts/format/).

Visual polish includes accessibility. WCAG's text contrast criterion generally uses 4.5:1, with 3:1 for qualifying large text and specified exceptions. Non-text contrast has separate rules for relevant controls and graphical information. An alternative perceptual contrast metric can inform craft, but must not substitute for the adopted WCAG test. [Text contrast](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html), [Non-text contrast](https://www.w3.org/WAI/WCAG22/Understanding/non-text-contrast.html).

## The Micro workflow

1. **Define the visual brief after the job.** Select adjectives that can change a design decision, such as calm, precise, playful, or editorial. Translate them into density, typography, contrast, spacing, imagery, tone, and motion choices. “Premium” alone is too vague. Record the task context, chosen platform, and constraints before generating mockups.
2. **Research complete references.** Use AppLlama for mobile flows and first-party product examples for web patterns. Record the observed screens and states, source, why the pattern fits, and what must differ. A screenshot can demonstrate visual arrangement; it does not establish conversion, accessibility, or usability. Do not reproduce trademarks, proprietary art, or exact product identity.
3. **Compare a few intentional directions.** Use representative content and the same critical journey in each variant. Evaluate hierarchy, readability, control clarity, and fit to the chosen identity. Preserve the owner's selection and unresolved questions. Avoid evaluating a mostly empty attractive mockup against a dense real app.
4. **Define the smallest token set.** Start with surface, foreground, subdued text, borders, accent, focus, success, warning, destructive, spacing, typography, radii, and motion roles. Separate semantic roles from palette values. Add product-specific visualization colors when needed and specify non-color distinctions for meaningful data.
5. **Build component contracts.** Document accessible names, variants, density, focus, keyboard behavior, error/pending states, content constraints, and source dependencies. Prefer composition with a small understandable interface. Avoid a universal component with many unrelated switches.
6. **Review actual screens.** Use the running app with realistic synthetic data, narrow and wide views, selected themes, large text, and interruptions. Check the relationship between hierarchy and the user's next action. Save reviewed evidence alongside the release candidate.

Recommended artifacts:

| Artifact | Minimum contract |
| --- | --- |
| `design-direction.md` | Chosen identity, comparative references, rationale, constraints, typography and density |
| Token source | Semantic roles, concrete values, ownership, supported themes, generated targets where needed |
| Component inventory | Reused/new control, behavior owner, state coverage, implementation source |
| Fixture route or stories | Representative content, long text, empty/error/pending states, narrow layout |
| `design-review.md` | Build, screenshots, findings, accepted differences, manual interaction evidence |

These may be sections of Micro's existing design artifact. Do not create duplicate authoritative files that disagree.

## Platform and library choices

| Choice | Use when | Conditions and alternative |
| --- | --- | --- |
| Native HTML controls | Browser semantics fit the task | Style carefully; use a tested composite primitive when native behavior is insufficient |
| Radix or Base UI | React needs dialogs, menus, comboboxes, or other complex controls | Select one family per control purpose; inspect APIs, licenses, maintained versions, and composition behavior |
| Existing component collection | It fits the product and already has local coverage | Treat copied source as owned code; upstream marketing does not discharge maintenance |
| Material components and theming | Android conventions fit the target app | Compose also supports custom design systems; a brand can differ without inventing every control |
| Sonner | A brief non-blocking web notification is appropriate | Keep important errors and recovery visible in the relevant content; toast alone is insufficient |
| Fixture route | A small product needs repeatable visual states | Add Storybook when reuse and state coverage make its maintenance worthwhile |

Radix and Base UI document built-in focus and keyboard support while retaining application responsibilities such as labels and visible focus. Test the composition you ship. Android's Compose guidance distinguishes Material Design 3 from custom systems. Sonner is Emil's React toast library; this names a purpose, not a mandatory package in every app. [Radix accessibility](https://www.radix-ui.com/primitives/docs/overview/accessibility), [Base UI accessibility](https://base-ui.com/react/overview/accessibility), [Compose design systems](https://developer.android.com/develop/ui/compose/designsystems), [Sonner](https://sonner.emilkowal.ski/).

Vaul remains an existing approved LifeOS dependency, but its upstream README states that the repository is unmaintained. Preserve current justified use and assess new adoption separately, including alternatives, owned fixes, gesture/accessibility evidence, and exit cost. Do not equate a respected author's package with guaranteed ongoing maintenance. [Vaul maintenance notice](https://github.com/emilkowalski/vaul).

## Risk-tiered acceptance

| Tier | Observable predicate |
| --- | --- |
| Prototype | Chosen direction uses representative content; controls and hierarchy express the main task; reference attribution and untested states are recorded |
| Public release | Required states render in the fixture set; contrast and relevant target sizing pass; no unintended clipping/overflow appears in the declared viewport/text/theme matrix; keyboard and assistive-technology checks from P02 pass |
| Shared factory component or consequential flow | Behavior and accessibility contracts are independently reviewed; downstream products are tested against the candidate change; breaking changes and migration steps are explicit |

WCAG 2.2 AA's pointer-target criterion is 24 by 24 CSS pixels with specific exceptions; 44px web hit areas are a product choice or stricter criterion, while Android recommends 48dp. Preserve these units and distinctions. [WCAG target sizing](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html), [Android targets](https://developer.android.com/guide/topics/ui/accessibility/views/apps-views).

Storybook can combine component behavior, accessibility, and visual checks. Playwright screenshot comparisons need stable browser, fonts, dimensions, data, and rendering environment. Baseline updates are reviewed design changes; an automatic snapshot update merely records the new image. [Storybook testing](https://storybook.js.org/docs/writing-tests), [Playwright visual comparisons](https://playwright.dev/docs/test-snapshots).

## Handoff, implementation, and limits

Handoff should name real component variants, semantic token roles, content, responsive behavior, assets and licenses, states, focus behavior, and acceptance examples. A Figma file can communicate structure; the implementation remains responsible for functional behavior and platform constraints. Keep design references and code contracts aligned through review rather than assuming generated markup is production-ready.

Start with per-product visual briefs and token roles. Add reusable fixture coverage next. Establish shared components after repeated verified use, then automate token exchange or design-to-code mappings where they remove real duplication. Vercel's interface guidelines are useful implementation review prompts for web apps, not normative standards. [Vercel interface guidelines](https://github.com/vercel-labs/web-interface-guidelines).

The retained Micro studio skill routes app-design guidance, and its brief/artifacts carry visual direction and references. The earlier LifeOS studio offered vibe selection and reference capture at [historical revision e04f14e](https://github.com/Samylay/LifeOS/tree/e04f14e/app/src/app/micro); concurrent user work removed that UI and its API from the current checkout. The shared component lifecycle, token interchange, fixture matrix, and reviewed visual baselines described here are proposed additions. Existing LifeOS header and motion rules remain local requirements. Applying them does not certify every Micro product's UI or require every product to share LifeOS's appearance.
